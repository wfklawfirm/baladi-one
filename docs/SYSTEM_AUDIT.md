Date: 2026-11-25 · Branch `dev` · Method: read-only review of the repository (code, migrations 0001–0020, existing docs). **No database, Supabase, Vercel or network access was used.** Nothing here was verified against the live database: where a conclusion depends on live data (who is a demo account, which migrations are applied, table grants), it is marked *needs live check*.

Scope notes
- Migrations `0024_procurement_ext.sql` and `0025_administration.sql` appeared in the working tree (untracked) while this audit ran. They are not part of this audit beyond a mechanical check (every function is `SECURITY DEFINER` with a fixed `search_path`, gated by `_council_muni()`, revoked from `public, anon`). They inherit the weaknesses in section 2 (demo and clerk behaviour), because they reuse the same pattern.
- Other workers were adding code in parallel while this audit ran (new untracked folders such as `app/staff/finance/closing`, `expenditure`, `lifecycle`, `app/staff/council/[id]/votes`, `app/staff/admin`, `app/staff/legal/updates`, and `lib/admin.ts`). Those were **not** audited; the "Missing" list in section 3.3 describes the committed state (HEAD `fc64cc7`) and may already be partly out of date. Re-run this audit once that work is merged.
- This is a technical and structural audit, not legal advice. Legal conclusions rest on `docs/LEGAL_AUDIT.md`, which itself says the sources are secondary and every rule is `pending_review`.

## 1. Classification legend

| Label | Meaning used here |
|---|---|
| LEGALLY VERIFIED | Rule checked against an official primary text by a qualified person. **Nothing in the system currently earns this label.** |
| IMPLEMENTED BUT LEGALLY UNVERIFIED | Code does what it says; the legal basis is from secondary sources or not reviewed |
| PARTIALLY IMPLEMENTED | Some of the required function exists; gaps listed |
| INCORRECT LEGAL IMPLEMENTATION | Code contradicts the legal text it cites |
| MISSING LEGAL REQUIREMENT | A requirement with no implementation |
| NOT APPLICABLE | No legal or security dimension |
| SECURITY RISK | Authorisation, abuse or exposure weakness |
| DATA INTEGRITY RISK | Records can be wrong, lost, duplicated or silently altered |

"Validation" column: **DB** = enforced inside the RPC/constraint (cannot be bypassed by calling the API directly); **FE** = only in the browser or in the Next.js server action (bypassable by calling PostgREST with a valid session); **DB+FE** = both.

Important context for every "DB" claim below: the app uses the public anon key plus the user's session, and Supabase PostgREST exposes every function in `public` that the role may execute. So a logged-in user can call any granted RPC directly. Server actions are convenience, not a security boundary.

## 2. Findings that cut across modules

| # | Class | Finding | Evidence |
|---|---|---|---|
| X1 | SECURITY RISK | **Demo accounts can write real data.** The home page of the demo municipality (`/m/demo`) has public one-click buttons that sign in with shared demo staff/mayor accounts (`enterDemo`). The demo mayor passes `_council_muni()`, so every council/finance/project/contract RPC runs for that municipality. Those RPCs only *stamp* new rows with `is_demo`; they never refuse to act on a row where `is_demo = false`. Worst case: `finance_add_line` does `insert into fiscal_year ... on conflict do nothing` then attaches a new line to the existing (real) fiscal year with `is_demo = fy.is_demo = false`, so a demo user can add real-looking budget lines to a real year without knowing any ID. ## 4. Correctly implemented points (so the picture is not one-sided)

- Every `SECURITY DEFINER` function in 0001–0025 sets a fixed `search_path`.
- Council/finance/project/contract RPCs derive the municipality from the session (`_council_muni()`) and filter every child lookup by it; the only parameter-driven municipality is `admin_create_staff(p_muni_slug)` and the public `submit_report(p_slug)` (by design).
- Money is `numeric(14,2)` everywhere; currencies are never summed together; rates return null rather than 0; partial settlement and over-commitment are blocked in the database under row locks (`for update`).
- Tacit-approval exclusions, audit-bureau base date, 10-working-day standstill and objection block were corrected in 0020 and have unit tests for the date arithmetic (`lib/council.test.ts`).
- Report export neutralises spreadsheet formulas (`lib/reportXlsx.test.ts`, `lib/reportBuild.test.ts`).
- Citizen tracking codes are stored hashed.
- No service-role key is used by the application.
